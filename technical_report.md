# Технический отчёт: система прогнозирования академической успеваемости и стипендиального риска

**Дата:** 28.05.2026

---

## 1. Общее описание системы

Анализируемый проект состоит из двух Python-скриптов, реализующих конвейер (pipeline) машинного обучения для прогнозирования академической успеваемости студентов российских вузов. Система предсказывает вероятность того, что студент сохранит "чистый академический результат" в следующем семестре, то есть завершит его без блокирующих оценок (тройки, двойки, незачёты, неявки) и без пересдач. Согласно правилам российского высшего образования, чистый результат в семестре N+1 даёт право на стипендию, выплачиваемую в семестре N+2. Таким образом, модель выступает как система раннего предупреждения на один семестр вперёд.

Первый скрипт (`scholarship_predict_histgb.py`) -- каноническая версия, работающая со всем массивом данных по студентам очной формы обучения. Второй скрипт (`scholarship_predict_histgb_bachelors_sem2_3.py`) -- изолированная копия, работающая с предварительно отфильтрованным срезом: только бакалавры очной формы, только студенты, присутствующие одновременно во 2-м и 3-м семестрах (987 человек). Оба скрипта идентичны по логике; второй отличается лишь входным файлом данных и выходной папкой.

В качестве алгоритма используется `HistGradientBoostingClassifier` из scikit-learn -- гистограммный градиентный бустинг, близкий по поведению к LightGBM. Он поддерживает нативную обработку пропущенных значений (NaN), что критически важно для данных, в которых семестры с исключительно зачётными (pass/fail) дисциплинами не имеют средних баллов.

---

## 2. Архитектура конвейера

Конвейер организован в пять последовательных этапов, каждый реализован отдельной функцией. Точка входа -- функция `main()`, которая разбирает аргументы командной строки (`--data` для пути к файлу данных, `--output` для папки результатов) и последовательно вызывает все этапы.

**Этап 1 -- Загрузка данных** (`load_data`): чтение xlsx-файла, первичная фильтрация и подготовка целевых колонок.

**Этап 2 -- Конструирование признаков** (`build_features`): дедупликация записей, агрегация по дисциплинам, вычисление статистик на уровне (студент, семестр).

**Этап 3 -- Построение обучающих пар** (`build_pairs`): создание переходов "семестр N -> семестр N+1" для каждого студента.

**Этап 4 -- Обучение модели** (`train_model`): разделение данных, настройка и обучение HistGradientBoosting.

**Этап 5 -- Оценка и сохранение** (`evaluate_and_save`): расчёт метрик, сравнение с бейзлайнами, сохранение артефактов.

## 3. Константы и словари

Скрипт определяет набор словарей и множеств, кодирующих правила российского высшего образования.

`SEMESTER_MAP` преобразует текстовые названия семестров в числовой порядковый номер (от 1 до 10). `GRADE_MAP` переводит текстовые отметки в числовую шкалу: "Отлично" = 5, "Хорошо" = 4, "Удовлетворительно" = 3, "Неудовлетворительно" = 2, "Зачтено" = 4 (приравнивается к "хорошо" для числовых расчётов), "Не зачтено" и "Неявка" = 2.

Множество `SCHOLARSHIP_BLOCKING_GRADES` содержит четыре отметки, которые блокируют право на стипендию: "Удовлетворительно", "Неудовлетворительно", "Не зачтено" и "Неявка".

`PASS_FAIL_CONTROL_TYPES` и `PASS_FAIL_GRADES` определяют зачётные дисциплины, не вносящие вклад в средний балл (GPA). Основной критерий -- вид контроля "Зачет"; текстовые отметки "Зачтено" / "Не зачтено" служат дополнительной проверкой.

Словарь `DEDUP_PRIORITY` задаёт приоритеты видов контроля для дедупликации: когда одна и та же дисциплина представлена несколькими строками (экзамен + курсовая работа), сохраняется запись с наименьшим приоритетом (экзамен = 0, зачет с оценкой = 1, курсовые = 2, зачет = 3). Это гарантирует, что при подсчёте доли пятёрок и троек используется оценка за основной вид контроля.

`KEPT_VEDOMOST_TYPES` перечисляет типы ведомостей, которые не удаляются из данных: "Основная", "Перезачет", "Пересдача", "Пересдача с комиссией". `RETAKE_VEDOMOST_TYPES` -- подмножество двух последних, обозначающее пересдачи.

`CLASS_B_LABELS` определяет четырёхклассовую диагностическую разметку переходов: 1 = чисто->чисто, 2 = чисто->провал (потеря стипендии, ключевой случай), 3 = провал->чисто (восстановление), 4 = провал->провал.

## 4. Источники данных и схема

### 4.1. Основной датасет

Каноническая версия конвейера работает с файлом `ГОСТ Р 70946-2023-Приложение-8_sorted.xlsx`, содержащим построчные записи академической успеваемости студентов. Файл находится в папке `data/`, не включён в систему контроля версий (gitignored) и не должен передаваться во внешние системы в сыром виде. Поиск файла реализован через `find_data_file` с несколькими паттернами имён, включая glob-подстановки, чтобы учесть вариации в именовании.

### 4.2. Срезовый датасет

Срезовая версия использует файл `output_bachelors_both_sem2_3_ochnaya.xlsx` -- 18 524 строки x 17 столбцов, один лист `Sheet1`. Схема полностью идентична основному файлу: те же 17 столбцов, те же соглашения по кодированию. Все константы канонического скрипта (`SEMESTER_MAP`, `GRADE_MAP`, `KEPT_VEDOMOST_TYPES`, `DEDUP_PRIORITY` и др.) применимы без изменений. Единственное отличие -- предварительная фильтрация: бакалавриат, очная форма, только 2-й и 3-й семестры. Слово "both" в имени файла указывает, что все 987 уникальных студентов присутствуют в обоих семестрах -- это готовый набор переходов 2->3 без пропущенных строк.

В папке `data/` также присутствует файл-сиблинг `output_bachelors_sem2_3_ochnaya.xlsx` (~3.4 МБ) -- предположительно тот же срез бакалавров, но без фильтра "присутствует в обоих семестрах". Этот файл конвейером не используется; взаимозаменяемость с основным срезовым файлом не подтверждена.

### 4.3. Схема данных и неиспользуемые столбцы

Оба датасета содержат 17 столбцов. Конвейер потребляет из них следующие: `ЗачетнаяКнижка` (идентификатор студента), `ПериодКонтроля` (текстовое название семестра), `ФормаОбучения`, `ТипВедомости`, `ВидКонтроля`, `Дисциплина`, `ИтоговаяОтметка` (текстовая итоговая оценка), `Пересдача` (балл по 100-балльной шкале за пересдачу), `Комиссия` (балл за комиссионную пересдачу).

Ряд столбцов намеренно не используется конвейером:

- `ПерваяАттестация`, `ВтораяАттестация`, `ТретьяАттестация` -- промежуточные оценки преподавателя в течение семестра по 100-балльной шкале. Эти данные являются upstream-компонентами итоговой отметки того же семестра N: они "схлопываются" в `ИтоговаяОтметка`, которая уже используется конвейером (как `grade_num`, и косвенно через `gpa_overall`, `min_grade`, `share_5`, `share_3`). Для задачи прогнозирования N->N+1 добавление промежуточных баллов рядом с итоговой оценкой не несёт дополнительной информации. Эти данные полезны для другой задачи -- внутрисеместрового прогнозирования (предсказание итоговой оценки по промежуточным аттестациям до экзамена).
- `Экзамен` -- 100-балльный экзаменационный балл. Аналогично промежуточным аттестациям, это upstream-компонент `ИтоговаяОтметка`, не дающий дополнительной информации для задачи N->N+1.
- `КодПреподавателя` -- идентификатор преподавателя.
- `УчебныйПлан` -- код учебного плана.
- `УровеньПодготовки` -- уровень образования (бакалавриат, магистратура и т.д.).
- `ПересдачаДляДиплома` -- флаг пересдачи для допуска к дипломной защите.

Целевая переменная `clean_record` вычисляется строго из `ИтоговаяОтметка` + `Пересдача` + `Комиссия` + `ТипВедомости`.

### 4.4. Терминологическая ловушка: N+1 vs N+2

Модель берёт признаки из семестра N и предсказывает `clean_record` в семестре N+1. Упоминание "N+2" в документации относится исключительно к семестру, в котором по правилам российских вузов выплачивается государственная стипендия, заработанная чистым результатом в N+1. Семестр N+2 не является ни отдельным предсказанием, ни входом модели. Стипендия в семестре N+1 определяется результатами текущего семестра N и не нуждается в прогнозе -- она уже известна.

## 5. Этап 1: загрузка и очистка данных

Функция `find_data_file` ищет xlsx-файл в папке `data/` по нескольким шаблонам имён. Каноническая версия использует паттерны с подстановкой (glob), срезовая версия -- единственное точное имя файла.

Функция `load_data` выполняет следующие операции:

Чтение xlsx-файла с листа `Sheet1`. Преобразование столбца `ПериодКонтроля` в числовой номер семестра через `SEMESTER_MAP`; строки с нераспознанным семестром отбрасываются. Фильтрация по форме обучения: остаются только записи с `ФормаОбучения == "Очная"`. Фильтрация по типу ведомости: остаются только записи из `KEPT_VEDOMOST_TYPES`.

Далее выполняется дедупликация пересдач. Для каждой комбинации (студент, семестр, дисциплина) строится множество ключей, для которых существует запись типа "Основная". Пересдачные строки, дублирующие существующую "Основную" запись, удаляются; остаются только "сиротские" пересдачи (те, для которых нет парной "Основной" строки). Это предотвращает двойной подсчёт оценок.

Создаются три производных столбца. `grade_num` -- численная оценка через `GRADE_MAP`. `is_scholarship_blocking` -- бинарный флаг, равный 1, если итоговая отметка входит в `SCHOLARSHIP_BLOCKING_GRADES`. `has_retake` -- флаг пересдачи, равный 1, если балл по столбцу "Пересдача" или "Комиссия" больше нуля, либо итоговая отметка -- "Неявка". Для сиротских пересдачных строк флаг принудительно устанавливается в 1.

Особая обработка перезачётов: для записей типа "Перезачет" оба флага (`is_scholarship_blocking` и `has_retake`) принудительно обнуляются, поскольку перезачёт из предыдущего образования не может блокировать стипендию и не является пересдачей. При этом оценки перезачётов учитываются в GPA и в общем числе дисциплин.

## 6. Этап 2: конструирование признаков

Функция `build_features` превращает набор построчных записей (одна строка = один предмет у одного студента) в агрегированные строки уровня (студент, семестр).

**Шаг 1: дисциплинарная агрегация.** Для каждой уникальной тройки (студент, дисциплина, семестр) вычисляются агрегаты: `disc_any_block` (была ли хотя бы одна блокирующая оценка), `disc_any_retake` (была ли пересдача), `disc_min_grade` (минимальная оценка). Это нужно, потому что одна дисциплина может быть представлена несколькими строками (экзамен + курсовая), и агрегат фиксирует "худший случай".

**Шаг 2: дедупликация.** Каждой строке назначается приоритет по виду контроля через `DEDUP_PRIORITY`. Данные сортируются по (студент, дисциплина, семестр, приоритет, оценка), после чего дубликаты удаляются с сохранением первой строки. Таким образом, для каждой дисциплины остаётся одна запись с наиболее значимым видом контроля.

После дедупликации обратно присоединяются дисциплинарные агрегаты: `is_scholarship_blocking` заменяется на `disc_any_block`, `has_retake` -- на `disc_any_retake`, а `grade_num` берётся как минимум из текущей оценки и `disc_min_grade`. Это гарантирует, что даже если после дедупликации осталась строка с хорошей оценкой, в статистику попадёт худшая оценка по дисциплине.

**Шаг 3: разделение на оцениваемые и зачётные дисциплины.** Признак `is_pass_fail` устанавливается по виду контроля `Зачет` или по текстовым отметкам "Зачтено" / "Не зачтено". Дисциплины с оценками (не зачётные) формируют подмножество `df_graded`.

**Шаг 4: семестровая агрегация.** На уровне (студент, семестр) вычисляются следующие признаки:

- `n_subjects` -- общее количество уникальных дисциплин.
- `n_blocks` -- количество предметов с блокирующими оценками.
- `n_retakes` -- количество предметов с пересдачами.
- `any_block` -- бинарный флаг наличия хотя бы одной блокирующей оценки.
- `any_retake` -- бинарный флаг наличия хотя бы одной пересдачи.
- `gpa_overall` -- средний балл, рассчитанный только по оцениваемым (не зачётным) дисциплинам.
- `min_grade` -- минимальная оценка по оцениваемым дисциплинам.
- `std_grade` -- стандартное отклонение оценок (мера стабильности).
- `share_5` -- доля пятёрок среди оцениваемых дисциплин.
- `share_3` -- доля троек среди оцениваемых дисциплин.
- `share_zachet` -- доля зачётных (pass/fail) дисциплин в общей нагрузке.

Доли `share_5` и `share_3` вычисляются по числовой оценке (`grade_num`), а не по текстовой отметке, чтобы исключить расхождения, вызванные заменой оценки на `disc_min_grade`.

**Шаг 5: определение целевой переменной.** Столбец `clean_record` устанавливается в 1, если у студента в данном семестре нет ни одной блокирующей оценки и ни одной пересдачи (`any_block == 0` и `any_retake == 0`). Для студентов первого семестра никаких исключений не делается: если есть блокирующая оценка, чистого результата нет.

## 7. Этап 3: построение обучающих пар

Функция `build_pairs` формирует обучающую выборку, в которой каждая строка -- это переход между двумя последовательными семестрами одного студента.

Для каждого студента семестры упорядочиваются по номеру. Для каждой пары (семестр N, семестр N+1), где N+1 = N + 1 (строго следующий семестр), создаётся одна обучающая строка: признаки берутся из семестра N, а целевая переменная `target_clean_next_sem` -- значение `clean_record` из семестра N+1. Непоследовательные семестры (например, 3->5 при отсутствии 4-го) пропускаются, поскольку признаки одного семестра не предназначены для предсказания на два шага вперёд.

Один студент может дать несколько пар за свою карьеру (2->3, 3->4, 4->5 и т.д.). В срезовой версии (бакалавры, семестры 2 и 3) каждый студент даёт ровно одну пару.

Дополнительно создаётся признак `had_clean_current_sem` -- копия `clean_record` текущего семестра. Это один из ключевых предикторов: если студент чист в текущем семестре, он с высокой вероятностью останется чистым в следующем.

Формируется диагностический четырёхклассовый столбец `class_B` через функцию `variant_b`: класс 1 (чисто->чисто), класс 2 (чисто->провал), класс 3 (провал->чисто), класс 4 (провал->провал). Этот столбец используется только в отчётности, не в обучении.

## 8. Этап 4: подготовка данных и обучение модели

### 8.1. Подготовка признаков

Функция `_prepare_features` формирует матрицу признаков `X` и вектор целевой переменной `y`. Из столбцов исключаются служебные колонки: идентификатор студента (`ЗачетнаяКнижка`), целевая переменная, номер целевого семестра, четырёхклассовая метка и текущий `clean_record`.

Пропущенные значения (NaN) намеренно оставляются для числовых признаков, таких как `gpa_overall` и `min_grade`. Значение NaN возникает в семестрах, состоящих исключительно из зачётных дисциплин, и является легитимным: заполнение нулём было бы некорректным, так как 0 не входит в шкалу оценок 2-5. HistGradientBoosting обрабатывает NaN нативно, обучая оптимальное направление разбиения на каждом узле дерева.

Единственное исключение -- `std_grade`, которое заполняется нулём при NaN: это случается, когда в семестре ровно одна оцениваемая дисциплина, и стандартное отклонение математически не определено.

Итоговый набор признаков содержит 13 переменных: `sem_num`, `n_subjects`, `n_blocks`, `n_retakes`, `any_block`, `any_retake`, `gpa_overall`, `min_grade`, `std_grade`, `share_5`, `share_3`, `share_zachet`, `had_clean_current_sem`.

### 8.2. Разделение на обучающую и тестовую выборки

Функция `_split_by_students` реализует разбиение 80/20 на уровне студентов, а не на уровне строк. Все пары одного студента попадают целиком либо в обучающую, либо в тестовую выборку. Это предотвращает утечку информации: если бы строки одного студента разделились между выборками, модель могла бы "подсматривать" паттерны конкретного человека.

Используется фиксированный `random_state=42` для воспроизводимости результатов.

### 8.3. Обучение HistGradientBoosting

Перед обучением вычисляются веса примеров через `compute_sample_weight("balanced", y_train)`. Это компенсирует дисбаланс классов: если, например, 70% примеров имеют чистый результат, а 30% -- нет, то примеры меньшинства получают пропорционально больший вес.

Гиперпараметры модели:

- `max_iter=1000` -- максимальное число деревьев (итераций бустинга).
- `learning_rate=0.05` -- скорость обучения; малое значение обеспечивает плавную сходимость.
- `max_depth=5` -- максимальная глубина каждого дерева; ограничивает сложность модели.
- `min_samples_leaf=10` -- минимальное число примеров в листе; предотвращает переобучение на малых подгруппах.
- `l2_regularization=5.0` -- L2-регуляризация; штрафует чрезмерно большие веса в листьях.
- `early_stopping=True` -- механизм ранней остановки: обучение прекращается, если метрика на валидационном подмножестве не улучшается.
- `validation_fraction=0.15` -- 15% обучающей выборки выделяется для внутренней валидации ранней остановки.
- `n_iter_no_change=50` -- обучение останавливается, если за 50 итераций метрика не улучшилась.
- `scoring="roc_auc"` -- метрика ранней остановки -- ROC-AUC.

Важное ограничение: HistGradientBoosting не принимает явный `eval_set`, поэтому внутреннее валидационное подмножество формируется на уровне строк, а не студентов. Строки одного студента могут оказаться в обоих внутренних подмножествах. Это влияет только на момент остановки обучения, но не на целостность внешнего тестового разбиения.

## 9. Этап 5: бейзлайны, оценка и сохранение

### 9.1. Бейзлайны

Функция `_run_baselines` вычисляет пять простых правил для сравнения с моделью:

1. **Majority** -- всегда предсказывать наиболее частый класс в обучающей выборке.
2. **Persistence** -- предсказывать, что состояние следующего семестра будет таким же, как текущего (`had_clean_current_sem`).
3. **Rule: no blocking** -- предсказывать чистый результат, если нет блокирующих оценок и пересдач.
4. **GPA >= 4.0** -- чистый результат, если средний балл не ниже 4.0.
5. **GPA >= 4.2** -- чистый результат, если средний балл не ниже 4.2.

Для каждого бейзлайна рассчитываются Accuracy, F1 (macro) и ROC-AUC. В срезовой версии (бакалавры, семестры 2->3) отмечается, что модель исторически уступает бейзлайну `gpa_4.2` (~80% против ~82%) из-за малого объёма данных (~800 обучающих пар) и однородности направления перехода.

### 9.2. Метрики модели

На тестовой выборке вычисляются: общая точность (Accuracy), F1-мера (macro-усреднение), ROC-AUC по вероятностям. Строится матрица ошибок бинарной классификации и развёрнутый classification report (precision, recall, F1 для каждого класса).

### 9.3. Четырёхклассовый анализ

Бинарные предсказания модели комбинируются с наблюдаемым текущим состоянием (`had_clean_current_sem`) для получения четырёхклассовых предсказаний. Строится матрица ошибок 4x4 и вычисляется точность для каждого из четырёх классов переходов. Особое внимание уделяется классу 2 (чисто->провал): это практически значимый случай потери стипендии.

### 9.4. Подгрупповой анализ

Отдельно оцениваются две подгруппы: студенты с чистым текущим результатом (`had_clean=1`) и студенты с нечистым (`had_clean=0`). Для каждой подгруппы рассчитываются свои метрики и classification report. Это позволяет понять, насколько хорошо модель работает для "стабильных" и "нестабильных" студентов.

### 9.5. Важность признаков

Используется перестановочная важность (`permutation_importance`) на тестовой выборке с метрикой ROC-AUC и 5 повторами. HistGradientBoosting не предоставляет атрибут `feature_importances_`, поэтому перестановочный метод -- единственный корректный вариант. Отрицательные значения обрезаются до нуля, после чего значения нормализуются так, чтобы их сумма составляла 1.0 (для интерпретации как относительных весов).

### 9.6. Посеместровая разбивка

Для каждого значения `sem_num` в тестовой выборке (при наличии >=10 примеров) вычисляются Accuracy и ROC-AUC перехода N->N+1. Это позволяет обнаружить семестры, на которых модель работает хуже (например, из-за нетипичного состава дисциплин).

### 9.7. Выходные артефакты

Система сохраняет следующие файлы:

- `predictions.csv` -- построчные предсказания для тестовой выборки: идентификатор студента, номер семестра, вероятность чистого результата, бинарное предсказание, фактический результат, четырёхклассовые метки, показатель риска (`risk_score = 1 - prob_clean`).
- `scholarship_model.joblib` -- сериализованная модель через joblib для последующего использования.
- `summary.md` -- технический отчёт в формате Markdown с таблицами метрик.
- `model_card.json` -- карточка модели в JSON: тип, целевая переменная, список признаков, метрики, бейзлайны, посеместровая точность, гиперпараметры.
- `report_human.md` -- отчёт для нетехнических заинтересованных лиц на русском языке.

Он включает: объяснение того, что предсказывает модель; объём обучающих и тестовых данных; точность и сравнение с простыми правилами; анализ по четырём категориям переходов с акцентом на "срыв успеваемости" и "восстановление"; распределение студентов по уровням риска (высокий < 30%, средний 30-60%, низкий > 60%); пять наиболее важных факторов с русскоязычными описаниями из словаря `FEATURE_DESCRIPTIONS`.

## 11. Различия между двумя скриптами

Второй скрипт (`scholarship_predict_histgb_bachelors_sem2_3.py`) является осознанной полной копией первого, а не обёрткой над ним. Это архитектурное решение обеспечивает изоляцию экспериментов на срезе ценой дублирования кода. Различия:

- Входной файл: `output_bachelors_both_sem2_3_ochnaya.xlsx` (предварительно отфильтрованный срез бакалавров, очная форма, семестры 2 и 3, 987 студентов).
- Выходная папка: `outputs/histgb_bachelors_sem2_3/`.
- Заголовок human report содержит указание среза: "бакалавриат, очная форма, переход семестр 2 -> семестр 3".
- Каждый студент даёт ровно одну обучающую пару (семестр 2 -> семестр 3).
- В документации отмечено, что на этом срезе модель исторически уступает бейзлайну `gpa_4.2` (примерно 80% против 82% точности), что объясняется малым объёмом данных и однородностью перехода.

Все остальные аспекты -- константы, логика загрузки, конструирование признаков, гиперпараметры модели, метрики оценки -- полностью идентичны.

## 13. Среда исполнения и зависимости

Проект разработан и запускается в среде Windows + PowerShell с виртуальным окружением Python (virtualenv в `.venv/`). Для корректного запуска рекомендуется использовать интерпретатор из виртуального окружения (`.venv/Scripts/python.exe`), чтобы избежать конфликтов с глобально установленным Python.

Основные зависимости конвейера зафиксированы в файле `requirements.txt`, привязанном к точному состоянию виртуального окружения, на котором был получен текущий `model_card.json`. В виртуальном окружении также установлены catboost, lightgbm, xgboost, matplotlib и plotly из предшествующих экспериментов (папка `legacy/`), однако каноническая версия конвейера их не использует.

## 14. Эксплуатационные замечания

### 14.1. Перезапись выходных данных

Каждый запуск конвейера полностью перезаписывает содержимое выходной папки (`outputs/histgb/` для канонической версии, `outputs/histgb_bachelors_sem2_3/` для срезовой). Перезаписываются файлы `model_card.json`, `predictions.csv`, `scholarship_model.joblib`, `summary.md` и `report_human.md`. Перед повторным обучением с изменёнными параметрами рекомендуется скопировать или переименовать папку предыдущего запуска, если его метрики важны для сравнения.

### 14.2. Синхронизация двух скриптов

Поскольку срезовый скрипт является полной копией канонического (~880 строк, а не обёрткой), любые изменения в логике загрузки данных, конструировании признаков или процедуре оценки в каноническом скрипте должны быть вручную перенесены в срезовый. Без явного переноса изменений скрипты будут расходиться. Это осознанный архитектурный компромисс: изоляция экспериментов ценой дублирования кода.

### 14.3. Устаревший код

В проекте может присутствовать папка `legacy/`, содержащая устаревшие реализации (в том числе с использованием CatBoost, LightGBM и XGBoost). Эти файлы намеренно выведены из области действия проекта: из них не следует импортировать, их зависимости не следует восстанавливать без явного указания.

## 15. Резюме

Система представляет собой завершённый конвейер машинного обучения для задачи бинарной классификации: прогноз сохранения чистого академического результата (и, как следствие, права на стипендию) в следующем семестре. Конвейер покрывает полный цикл от загрузки "сырых" данных до генерации готовых отчётов. Особое внимание уделено корректности предметной области: обработка перезачётов, дедупликация многокомпонентных дисциплин, разделение оцениваемых и зачётных предметов, студентоуровневое разбиение данных, нативная обработка пропусков. Намеренное исключение промежуточных аттестационных баллов и 100-балльных экзаменационных оценок из признакового пространства обосновано их коллинеарностью с итоговой отметкой -- эти данные полезны для внутрисеместрового, но не межсеместрового прогнозирования. Четырёхклассовый анализ переходов и распределение по уровням риска делают результаты интерпретируемыми для нетехнических заинтересованных лиц. Два скрипта -- канонический и срезовый -- обеспечивают гибкость экспериментов на разных подмножествах данных при сохранении единой методологии.
